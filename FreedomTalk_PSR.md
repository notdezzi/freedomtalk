# Portfolio Case Studies

## Real-time Messaging Platform

### Problem

Building a Discord-like messaging platform required addressing several fundamental challenges simultaneously. Users expect instantaneous communication with message delivery, typing indicators, and presence awareness—all while maintaining consistency across potentially millions of concurrent connections. Traditional HTTP polling approaches could not support the scale and responsiveness required, and naive WebSocket implementations often struggle with horizontal scaling, connection state management, and graceful degradation under network instability. The platform also needed to support complex channel structures (servers, DMs, voice channels) with different permission models, message retention policies, and real-time synchronization requirements. Architectural choices made early would determine whether the system could scale from thousands to millions of users without requiring complete rewrites.

### Solutions

The solution采用了 a hybrid architecture combining Next.js App Router for the web client, Fastify for the backend API, and Socket.io with a Redis adapter for real-time communication. The WebSocket layer was implemented as a singleton service with separate managers for concerns like connection lifecycle, room subscriptions, presence tracking, and typing indicators—ensuring clear separation of responsibilities. The Redis adapter enables horizontal scaling by broadcasting events across all server instances, allowing the system to add nodes without rewriting core logic. Message delivery uses a dual approach: new messages arrive via WebSocket for immediacy, while historical message pagination and search use REST endpoints served through TanStack Query's caching layer. The state management strategy uses Zustand for ephemeral UI state (modals, typing indicators, socket status) and TanStack Query for server state with optimistic updates and automatic cache invalidation. A comprehensive permission system with 34-bit flags allows fine-grained access control at the server, channel, and user levels, with a three-state model (allow, neutral, deny) that resolves hierarchically through roles. The infrastructure is containerized with Docker Compose, using PostgreSQL for persistent data, Redis for pub/sub and caching, TimescaleDB for time-series capabilities, and MinIO for S3-compatible file storage.

### Results

The architecture achieved immediate message delivery with typing indicators and presence updates working reliably across channels and direct messages. The permission system successfully handles complex access scenarios without performance bottlenecks, and the Redis adapter approach validated the horizontal scaling strategy. The monorepo structure with a shared package for types and schemas eliminated duplication and ensured type safety across frontend and backend boundaries. Playwright E2E tests and Vitest unit tests provide confidence in core functionality, while the feature-based component organization maintains maintainability as the codebase grows. The design system built on Tailwind CSS with semantic color tokens and a centralized modal system ensures UI consistency and allows rapid iteration on new features.

## Permission System

### Problem

A messaging platform with servers, channels, and user roles requires a flexible yet performant permission system that can handle thousands of permission checks per second. Discord's permission model is particularly complex because permissions are granted through roles, roles are hierarchical, and different channels can have role-specific overrides. The system needs to support granular controls at multiple levels (server, category, channel) while resolving conflicts deterministically and efficiently. Naive implementations that query the database for every permission check would create unacceptable latency at scale, while over-caching could lead to stale permissions and security vulnerabilities. The challenge was designing a system that is both flexible enough to support any permission scenario and fast enough to check in real-time during message delivery, voice connection attempts, and UI rendering.

### Solutions

The solution implements a 34-bit permission flag system where each bit represents a distinct capability, from basic actions like sending messages to administrative powers like managing servers. Permissions are granted through roles with an optional override at the channel level, creating a three-state model where a permission can be explicitly allowed, explicitly denied, or neutral (inheriting from parent). The resolution algorithm walks the hierarchy from channel overrides through roles to server defaults, applying bitwise operations to compute the final permission set efficiently without database queries. The permission middleware factory in the backend allows decorators-style permission checks on API routes, while the frontend uses a custom `useCan` hook that mirrors the backend resolution logic for UI decisions. This parallel implementation ensures that what the user sees matches what they can actually do. The permission flags are defined in the shared package, ensuring both frontend and backend reference the same canonical source of truth, and TypeScript types are auto-generated from the flag definitions.

### Results

The permission system handles all access control scenarios with minimal computational overhead. Bitwise operations allow permission resolution in constant time, and the shared schema eliminates inconsistencies between frontend and backend implementations. Role-based assignment with channel-level overrides provides administrators fine-grained control without requiring individual user permissions for every scenario. The three-state model allows administrators to grant broad permissions through roles while selectively denying specific actions in sensitive channels. The system scales to thousands of permission checks per second without database queries, making it suitable for real-time operations like voice connection validation and message delivery filtering.

## Voice and Video Infrastructure

### Solution

Voice and video communication requires WebRTC signaling with state management for who is in which channel, who is speaking, and how to route media between participants. The challenge is implementing an SFU (Selective Forwarding Unit) without deploying a separate media server, while maintaining integration with the existing permission system and real-time infrastructure. Network conditions vary across users, so the system must handle ICE candidate exchange, offer/answer negotiation, and connection state changes gracefully. Permissions for voice channels (connect, speak, mute others, move participants) need validation before establishing connections, and voice state must persist across server restarts while remaining consistent with actual active calls.

### Solutions

The voice infrastructure integrates Mediasoup directly into the Fastify application rather than deploying a separate media server. Voice state is tracked in the PostgreSQL database, allowing the system to recover state after restarts and maintain a single source of truth. WebSocket handlers manage the WebRTC signaling flow—offer, answer, and ICE candidates—with permission checks performed before allowing connection attempts. The system validates server membership and ban status, ensures users have the CONNECT permission for the target channel, and enforces speaking restrictions based on role configuration. For direct message voice calls, participant verification ensures only conversation members can join. The voice store on the frontend manages local state including connection status, participant lists, and audio stream handling, with a custom hook abstracting the Mediasoup client lifecycle. The architecture supports both server voice channels and DM calls using the same underlying infrastructure, with channel type determining the permission checks and participant validation logic.

### Results

The integrated SFU approach eliminates the operational complexity of managing a separate media server while still providing full WebRTC functionality. Voice state persistence in the database ensures that active calls can survive server restarts, and the permission system integration prevents unauthorized users from joining voice channels or speaking when they should not. The unified infrastructure for server and DM calls reduces code duplication, and the state management strategy keeps the UI consistent with actual connection status. The system handles network conditions through standard WebRTC mechanisms, with ICE candidate exchange allowing connections through NAT and firewalls.
